# Publicação da sincronização de rankings

A implementação fica desativada até implantação e configuração. O serviço atual gratuito do Render dorme sem tráfego; um timer dentro dele não é um agendador confiável.

1. Testar `schema.sql` em uma branch isolada do banco. Aplicar a migração ao banco de produção com conexão direta após o teste. O comando existente é `npm run migrate` em `Backend`; não expor a URL do banco.
2. Publicar o backend alterado. Manter `RANKING_SNAPSHOTS_ENABLED` desligado inicialmente para conservar o comportamento existente.
3. Gerar token aleatório dedicado (pelo menos 32 caracteres) e configurar `RANKING_SYNC_TOKEN` no Render. Adicionar o mesmo valor ao segredo `RANKING_SYNC_TOKEN` no GitHub e o endereço HTTPS completo `https://<serviço>/rankings/sync` ao segredo `RANKING_SYNC_URL`. Não copiar `DATABASE_URL` nem `API_TENNIS_KEY` para o GitHub. O workflow `.github/workflows/sync-rankings.yml` chama o endpoint a cada hora no minuto 17 UTC e pode atrasar ou não executar; verifique limites e faturamento do plano GitHub, alertas e inatividade do repositório. Não criar serviço pago sem autorização. O endpoint aceita somente POST autenticado, funciona com a leitura por snapshots desligada e registra falhas. Uma reserva temporária no banco evita chamadas concorrentes pelo endpoint e pelo CLI; um token impede publicações após a expiração da reserva. Para execução manual controlada, o comando `npm run sync-rankings` permanece disponível com acesso ao banco e à chave no ambiente do backend.
4. Executar uma tarefa e verificar as duas linhas em `ranking_snapshots` com versão e sucesso, os logs `ranking_sync_success`, e os dados reais comparados às listas oficiais. Confirmar uma segunda execução agendada sem intervenção; verificar também após novo deploy.
5. Só depois configurar `RANKING_SNAPSHOTS_ENABLED=true` no web service e fazer deploy. `GET /tennis?method=get_standings&event_type=ATP|WTA` passa a ler o snapshot diretamente do banco, com `Cache-Control: no-store`. `GET /rankings/status` mostra tentativa, resposta do provedor, validação, última mudança e erros, sem data oficial (não disponível na resposta). Uma ausência de snapshot retorna 503; não substitua dados do app por dados vazios.
6. Conferir tela e widget do iOS após abrir o app e comparar com `x-ranking-version` e os dados do endpoint. O app atual consulta o mesmo endpoint e continua a sincronizar seu armazenamento local; não é ele quem executa o job.

O limite de redução de 50% é uma heurística: pode rejeitar uma redução legítima ou aceitar uma resposta parcial maior. A primeira execução não tem contagem anterior para comparar. Antes de ativar em produção, confirmar cobertura completa com o fornecedor e operar monitoramento das falhas e da idade do último sucesso. O hash identifica conteúdo recebido e não prova data oficial. Uma falha de consulta não apaga o snapshot anterior; o agendador deve registrar falha e tentar novamente na próxima execução.
